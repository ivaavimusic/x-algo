## Technical Details

Fixes #255.

When a Following fetch returns 101 posts and filtering removes all of them, `selected_candidates` supplies no bottom ID. The cursor builder then reuses the incoming ID, so scrolling fetches the same empty page again. Deriving `bottom_tweet_id` from `retrieved_candidates` advances past the consumed page and makes older eligible posts reachable.

Validation on the published source with substitute search and internal types:

- A 160-post example (5 kept, 120 removed, 35 kept) exposes only 5 posts before the change and all 40 after it.
- The scrolling property passes all 300 generated timelines with the change; the original fails in the 103 cases containing a blocking filtered run.

The [reproduction workspace](https://github.com/user-attachments/files/33550321/x-algorithm-repro-92f0918.zip) is attached to #255. From its `harness` directory:

```sh
cargo test -p history_h --release --test following_pagination h1_minimal_witness -- --nocapture
cargo test -p history_h --release --test following_pagination pg1 -- --nocapture
```

The public release omits internal dependencies, so this validation does not build or run the complete home-mixer service. The separate refresh/gap-cursor problem described by the reproduction suite remains outside this change.
