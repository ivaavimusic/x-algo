## Problem

On 2026-10-12 the report still serves August 2026. Under the current rules September became the calendar target on Oct 10 (`minDaysAfterMonthEnd = 10`), so the served month is either capped by `under_the_hood_report_max_month_bucket` or falling back because September's data is not complete yet. The page cannot say which. It also tells everyone the report covers "last month", and the eligibility check says "10 or more posts in the prior month", both of which are wrong whenever the cap or the fallback applies.

## Change

1. **Wording corrections (always on).** The landing description no longer asserts "last month", and the eligibility label reads "10 or more posts in the report month". The mock fixtures use the same string.
2. **Report status (behind `under_the_hood_report_status_enabled`, default `false`).** The serving column already computes three months: the uncapped calendar target, the capped primary month, and the month actually served. With the switch on it reports them:
   - `periodStatus`: `current`, `capped` or `data_pending`.
   - `nextReportNotBefore`: the calendar floor for the month after the served one (month end + `minDaysAfterMonthEnd`, UTC). It is a "not before" date, not a promise.
   - New optional `UnderTheHoodReportInfo` fields with new field ids, selected in the query, mapped in `load.ts`, and rendered as one localized status line on the landing and report pages, for example: "September 2026 is not available yet; showing August 2026. Next report no earlier than 2026-11-10 UTC."
   - The JSON download's `notes` string gets the same sentence appended after the existing text, links intact, since the file has no page around it. The in-page RichText note is unchanged.
   - The JSON report gains one optional `periodStatus` object. No existing key is renamed, removed or reordered.
3. **README.** A short "Report schedule" paragraph stating the rules the code already applies, including the deliberate one-month lag.

## Safety

With the switch at its default, the JSON report and GraphQL response are unchanged apart from the two wording fixes. Field additions are optional with fresh ids. Both response branches (metadata-only and user row) populate the new fields.
