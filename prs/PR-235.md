## Problem

A report that says "1 of your 2,552 posts was labeled SPAM_HIGH_RECALL" gives the author nothing to act on. They cannot see the post, judge the call, or appeal it. The ID is present in the pipeline and dropped at aggregation: `UthDailyPostsJob.scala` reduces on `(logicalId, userId, day, label, createdMs)` and then destructures it as `case ((_, userId, day, label, createdMs), ...)`.

## Change

**Storage.**
- Each daily row and monthly aggregate keeps up to 20 post IDs per label.
- Ordered newest `createdMs` first, ties broken by the larger ID.
- The cap is one shared constant, `maxPostIdsPerLabel`, in `UnderTheHoodCommon.scala`.
- `postIdsTruncated` records when more existed.
- IDs come from the same `everApply` population and the same selected daily rows as the counts. The count arithmetic is unchanged and does not depend on the cap.
- The safety-label path, the tweet-flag path and the backfill job are all covered.

**Schema.** Optional `postIds` (`list<i64>`, annotated like sibling personal-data fields) and `postIdsTruncated` on `UthDailyPostLabel` and `UthPostLabelAggregate`, with new field ids. Older rows simply lack them.

**Serving (behind `under_the_hood_report_post_ids_max`, default `0` = off, clamped to 20).**
- Each post-label row gains `postIds` as decimal strings, never JSON numbers, since 64-bit IDs lose precision in JavaScript.
- It also gains `postIdsTruncated`.
- Rows without stored IDs (older months, takedown labels) report `postIdsAvailable: false`.
- At `0` the JSON is byte-identical to today.

**Page.** The page links each ID to `x.com/i/status/<id>`, says "showing N most recent" when truncated, and "Post IDs are not available for this label" when unavailable. Parsing uses a string-only parser.

**Docs.** `under-the-hood/POST_IDS.md` describes the path end to end.

## How this differs from #92

#92 targets the same gap. This version:
- caps at 20 instead of 1,000, bounding storage at the daily step;
- keeps IDs as strings end to end;
- gates serving behind a default-off switch;
- separates truncated from unavailable, so a partial list never reads as complete.

No code from #92 was reused.
